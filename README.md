# Bank Console App

Учебное консольное банковское приложение на Java: клиенты, депозитные счета
двух видов, транзакции, начисление процентов по месяцам и досрочное закрытие
депозита со сгоранием вознаграждения. Без внешних БД/облака — вся
персистентность реализована как таблицы в оперативной памяти.

## Быстрый старт

Требуется JDK 21+ и Maven 3.8+.

```bash
mvn clean package
java -jar target/bank-console-app.jar
```

Или без сборки jar, прямо из исходников:

```bash
mvn compile exec:java -Dexec.mainClass=com.bank.Main
```

Тесты (используют JUnit 5, подтягивается Maven'ом автоматически):

```bash
mvn test
```

## Архитектурные решения

**Богатая доменная модель (rich domain model).** Инварианты — "нельзя снять
деньги с накопительного депозита", "нельзя уйти в минус", "проценты сгорают
при досрочном закрытии" — реализованы методами самих классов `Account` /
`DepositAccount`, а не проверками в сервисах. Это защищает объект от перехода
в невалидное состояние независимо от того, кто и откуда его вызывает —
консоль, будущий REST-контроллер или тест.

**Наследование депозитов (Open/Closed Principle).** `DepositAccount` —
абстрактный класс с общей логикой (ставка, срок, начисления, дата окончания,
досрочное закрытие). `WithdrawableDepositAccount` и `AccumulativeDepositAccount`
переопределяют только `isWithdrawalAllowed()` и `getDepositType()`. Если в
будущем понадобится третий вид депозита (например, с капитализацией процентов
на отдельный счёт) — добавляется новый класс, ни одна существующая строчка
не меняется.

**Репозитории через интерфейсы (Dependency Inversion).** `CustomerRepository`,
`AccountRepository`, `TransactionRepository` — интерфейсы. Сейчас единственная
реализация — `InMemoryDatabase` (три `ConcurrentHashMap`, как три таблицы).
Чтобы подключить настоящую БД, достаточно написать `JdbcAccountRepository
implements AccountRepository` и т.д. — сервисы и доменные классы не изменятся
ни на строку. Это и есть путь к масштабированию, обозначенный в задании.

**Сервисный слой — только оркестрация.** `AccountService`, `TransferService`,
`InterestAccrualService` не содержат бизнес-правил — они генерируют id,
вызывают доменные методы и сохраняют результат (счёт + транзакцию) в
репозитории. Это разделение (SRP) делает сервисы тонкими и легко
тестируемыми без моков консоли.

**Перевод между депозитами** реализован как атомарная пара «снятие с
источника + пополнение получателя»: списание выполняется первым и обязано
пройти проверку `isWithdrawalAllowed()`/достаточности средств; только после
успешного списания выполняется зачисление. Это значит, что перевод С
накопительного депозита запрещён (как и прямое снятие), а перевод НА него —
разрешён (как и прямое пополнение). В README отдельно стоит отметить: в
реальной распределённой системе такая операция потребовала бы транзакции
БД или saga-паттерна; здесь всё выполняется в одном потоке, что для
консольного прототипа достаточно.

**Каждая операция — отдельная транзакция с собственным id**, включая
ежемесячное начисление процентов и обе стороны перевода (TRANSFER_OUT /
TRANSFER_IN). Id всех сущностей выдаёт один потокобезопасный
`IdGeneratorService` (`AtomicLong`), чтобы не плодить гонки при работе с
несколькими потоками.

**Досрочное закрытие.** `DepositAccount` отдельно отслеживает
`accruedInterestTotal` — сумму, начисленную за счёт `simulateMonths`. При
досрочном закрытии эта сумма списывается с баланса и **не удаляется** из
истории транзакций: вместо этого создаётся компенсирующая транзакция
`INTEREST_FORFEITED`, чтобы выписка оставалась полной и аудируемой (в
финансовых системах транзакции, как правило, не удаляют, а сторнируют).

## Ключевые допущения (там, где формулировка задания была неоднозначной)

- Фраза «Аккаунт (айди счета, номера счета для депозита (2))» истолкована
  как указание на два вида депозитных счетов, которые описаны в задании
  чуть ниже (с/без права снятия) — отсюда `WithdrawableDepositAccount` и
  `AccumulativeDepositAccount`, у каждого свой префикс номера счёта
  (`WD-000001` / `AC-000001`).
- «Уникальный код (почта, телефон, пароль — одно выбираем)» — реализовано
  как пара `(ContactType, значение)`: при регистрации клиент выбирает ровно
  один из трёх вариантов.
- Ставки заданы не как свободный ввод, а как таблица `InterestRateSchedule`,
  зависящая от типа депозита и срока, — потому что в задании явно перечислен
  конкретный набор значений (17 / 17.5 / 19 / 21 / 22.3), а не диапазон.
  Накопительный депозит закономерно даёт более высокую ставку, чем депозит
  с правом снятия — это соответствует реальной банковской практике.
- Помимо явно требуемого досрочного закрытия добавлено закрытие "по сроку"
  (`closeAtMaturity`) — сохраняет начисленные проценты, в отличие от
  досрочного. Это не обязательное требование, а логичное дополнение той же
  доменной модели.

## Пример сценария (то, что было прогнано вручную при проверке)

1. Открыть клиенту депозит `WD` на 6 месяцев со взносом 100 000 → ставка
   17.5%, дата окончания рассчитана автоматически (+6 месяцев).
2. Прогнать симуляцию на 2 месяца → две транзакции `INTEREST_ACCRUAL`
   (1 458.33 и 1 479.60 — процент считается от уже выросшего баланса),
   баланс 102 937.93.
3. Закрыть депозит досрочно → баланс возвращается к 100 000.00, в выписке
   появляется третья транзакция `INTEREST_FORFEITED` на −2 937.93.
4. Попытка перевода средств с накопительного депозита (`AC`) на другой счёт
   отклоняется с понятной ошибкой — снятие с него запрещено.
5. Симуляция 10 месяцев на 3-месячном депозите начисляет проценты только
   3 раза (`getRemainingMonths()` не даёт уйти за пределы срока).

## Кредиты

- Ставка 30% годовых, аннуитетный платёж, сроки 6/12/24/36 мес. (`domain/credit/Credit.java`).
- Общий лимит банка на выдачи — 1 000 000 (`CreditService`): считаются тела невозвращённых кредитов.
- Платежи списываются со счёта списания (депозит с правом снятия) в симуляции погашения
  (`CreditRepaymentService`, пункт меню 13).
- Если платёж не проходит, симуляция не останавливается: долг (остаток основного долга +
  проценты месяца) принудительно взыскивается со всех счетов клиента. Если долг не покрыт —
  все счета блокируются, кредит получает статус `DEFAULTED`; если покрыт — `CLOSED_BY_SEIZURE`.
- Вывод в консоль свёрнут: подряд идущие операции одного типа печатаются одной строкой
  (`console/TransactionFormatter.java`).

## Куда расти дальше

- Заменить `InMemoryDatabase` на JDBC/JPA-реализацию репозиториев — домен
  и сервисы не изменятся.
- Вынести `ConsoleApp` в отдельный модуль и добавить REST-слой (Spring Web
  или обычный `HttpServer`) поверх тех же сервисов.
- Добавить многопоточность на уровне заявок (например, обработка операций
  через очередь) — `IdGeneratorService` и `ConcurrentHashMap`-репозитории
  уже потокобезопасны, узкое место — не разделённые критические секции
  внутри отдельных операций `deposit`/`withdraw`/`transfer` (нужны блокировки
  по счёту при реальной многопоточной нагрузке).
- Мультивалютность: `Account` сейчас предполагает одну валюту; добавление
  поля `Currency` и валидации при переводах — расширение, а не переделка.
